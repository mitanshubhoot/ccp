# Agentic CCP: Architecture Deep Dive and Competitive Research

Nov 9, 2026 · @Claude

**Bottom line.** In design, Agentic CCP leads the documented competitors on evidence history and on limits for what agents may do: a write-once raw zone, append-only verdicts, bitemporal state, "models extract, code decides", and approvals pinned to a hash of what was approved (C). It is not yet a product: it is teaching-scale by its own spec, its code has verified defects inside those strengths (a typo can approve, the citation check can mark a false pass as verified, and a crash can lose a verdict), and no AI tier has been measured on a real model (D). Keep the core and rebuild the edges. On day 1, push the repo to a private remote so the CI it already has runs on every change. Then spend about nine to twelve weeks (17–24 engineer-weeks, estimated) fixing the verified defects and running the first evals on real models; until that is done, CCP should not handle real customer data or rely on a real model's output. After that, build what a first production customer needs: connectors that record whether each pull was complete, durable execution, signed-in reviewers, an API and a cloud deployment (Section F).

## A. Current Agentic CCP architecture

Agentic CCP (`agentic/ccp`) is a 21,515-line Python build of the whole compliance loop, written from `spec.md` v1.3 in 17 phases on 11–12 Sep 2026. Its data-integrity core is production-grade in design: an immutable raw zone, append-only entities, a bitemporal state table, and "models extract, code decides". Its integration layer is the thinnest part: three connectors, one live, and no credential, rate-limit or sync-completeness handling.

Scale today, verified from the repo at commit `3386899`:

| Dimension | Agentic CCP |
| --- | --- |
| Tenants | 2 fixture tenants (`acme`, `globex`) in `config/tenants.yaml` |
| Connectors | GitHub (fixture plus a live REST/GraphQL client), HRIS (fixture only), manual uploads (md, txt, text-layer PDF) |
| Tests | 10: 7 deterministic, 2 tier 2 (GH-4, HR-3), 1 tier 3 (HR-4) |
| Controls and frameworks | 9 controls mapped to a 6-criterion SOC 2 slice and an 8-control ISO 27001 slice |
| Agents | Tier-3 evaluator graph, Investigator, Policy Agent, Copilot (all LangGraph) |
| Code and tests | 21,515 lines in `ccp/`; 15 SQL migrations; 66 test files with 383 test functions |
| Interface | CLI only (`ccp/cli.py`); no API, UI or user identity |

### A.2 Integration lifecycle, end to end

There is no "customer connects an account" step: the GitHub token comes from `GITHUB_TOKEN` and tenants from a YAML file. From there:

1. **Pull.** `ccp ingest` calls `connector.pull(tenant)` with no cursor, so every run is a full pull (`landing.py:100`). The live GitHub client reads 7 REST endpoints and one GraphQL query (`github/client.py:1-13`).
2. **Land.** Each event is written under `data/raw/{tenant}/{connector}/{yyyy/mm/dd}/`, then inserted into `raw_events` with `ON CONFLICT DO NOTHING`; only a new row reaches `event_log` (`landing.py:50-77`).
3. **Normalize.** One ordered consumer per raw topic re-reads the raw file, runs the pure mapper, inserts observation rows and announces each new row on the `entities` topic (`normalize/consumer.py:66-85`).
4. **Resolve identity.** HR and GitHub persons are linked into a canonical person; ambiguous pairs go to a review queue and make the dependent tests `needs_review`.
5. **Trigger.** The impact consumer turns each entity change into evaluation requests, folding duplicates for the same subject inside 60 s (`impact.py:81-113`).
6. **Evaluate.** The evaluations consumer checks the tenant's daily budget, routes by tier and inserts the verdict idempotently on `evaluation_key` (`0005_state.sql:34`).
7. **Record state.** One `compliance_state` row per verdict supersedes the subject's chain head under an advisory lock (`bitemporal.py:125-135`). A `needs_review` verdict is written as a fact, not held back.
8. **Fan out.** Fails and `needs_review` verdicts go to the Investigator, whose proposals land in the approval stage. A clock producer re-enqueues subjects whose evidence passed `evidence_max_age` (`ccp/evaluators/clock.py`).
9. **Remediate and re-evaluate.** An approved proposal runs as a dry run by default; the re-pull flows back through steps 1–7, so a fixed issue shows as a new `pass` row superseding the `fail`.

### A.3 Compliance evaluation: how a verdict is made

The tier is fixed at authoring time in `ccp/knowledge/tests.yaml`, never chosen at run time: `deterministic` goes to tier 1, `interpretive` with one evidence type to tier 2, and two or more types to tier 3.

| Tier | Tests | What a model does | What decides | Confidence |
| --- | --- | --- | --- | --- |
| 1 Deterministic | GH-1, GH-2, GH-3, GH-5, HR-1, HR-2, HR-5 | Nothing; `tests/unit/test_layering.py` fails if a tier-1 module imports `ccp.llm` or `langgraph` | A pure function over entities | 1.0; `needs_review` only when an identity link is unresolved |
| 2 Extract-then-rule | GH-4, HR-3 | Fills a typed schema; each field cites a chunk id and a verbatim quote | A pure rule over verified fields (`ccp/evaluators/rules/`) | Field coverage × citation survival × retrieval percentile, with forcing caps |
| 3 Fixed workflow | HR-4 | Extracts per evidence type in a LangGraph workflow; a bounded tool loop runs only when a fetch finds nothing | A pure comparison, then a human gate below 0.70 | As tier 2, plus a 0.40 cap for an unresolved evidence type |

Evidence enters a prompt only through `prompt_guard.frame_evidence()`, which redacts secrets, wraps each chunk in a per-call random fence and caps confidence at 0.60 when it sees injection markers. After generation, `citations.py:87-129` drops any field whose quote is not found in the cited chunk. Only dates, providers and timeline text must also appear in their quote, so the fields that decide pass or fail accept any quote that is present (A.7). A verdict left without citations becomes `needs_review`.

### A.4 Agent execution

| Graph | Runs when | Tools (allowlist) | Produces | Persisted by |
| --- | --- | --- | --- | --- |
| Tier 3 evaluator | An HR-4 evaluation | 7 read tools; no prior verdicts, so it cannot anchor on them | A verdict, or an interrupt for review | The evaluations runner |
| Investigator | Every `fail` or `needs_review` verdict | Tier-3 set plus `get_verdict`, `list_findings`, `get_access_grants`, `get_control` | Root cause, missing evidence, actions from a closed enum | Its runner, one approval per action |
| Policy Agent | `ccp policy gap` or `draft` | `search_evidence` (policy documents only), `get_chunk`, `get_control`, `get_framework_rollup` | Gap report; Markdown draft under `data/drafts/` | Its runner; a draft becomes evidence only through a human upload |
| Copilot | A question in the REPL | All 13 read tools | Answer whose citations are checked for presence; at most 2 requested actions per turn | Its runner, after a typed `yes`, opens approvals |

Every tool takes the tenant from a closure, rejects extra arguments (`tools.py:35-36`) and answers off-list calls with an error result (`core.py:340-341`). Runs are bounded by token, dollar, wall-clock and tool-call budgets, checkpointed to Postgres under row-level security, and resumable from a separate process.

### A.5 Data, background work and failure handling

- **Append-only by grant.** The app role is granted only `SELECT` and `INSERT` on verdicts, compliance state, approvals, investigations, gap reports, policy drafts and Copilot answers, and likewise on the raw-event index and the entity tables, so it cannot rewrite history (migrations 0005 and 0011–0014; the `REVOKE` lines there only restate intent).
- **Entities are observations, not state.** Each row carries the source timestamp, and a view returns the latest per entity (`0003_entities.sql:100-102`). Only `compliance_state` is bitemporal (assumption A-7).
- **Each worker process runs one consumer and polls every 2 s** (`worker.py:67-103`, `cli.py:552-563`). Parallel topics make up to 5 attempts, then dead-letter; exhausting the tenant's daily budget, or a missing model key, parks a record instead of failing it.
- **Model errors are classified.** 429, 529 and timeouts back off and retry; 400s, schema refusals and per-run budget overruns dead-letter at once, so a model outage never produces a verdict. Retrieval degrades instead: an embedding or reranker outage caps confidence, and yields a `needs_review` verdict if lexical search also finds nothing.

### A.6 Security, isolation and evaluation

Isolation is enforced three times: a typed `TenantContext`, a `ScopedDB` that sets `app.tenant_id` per transaction, and forced row-level security on every tenant table, including vectors and LangGraph checkpoints. Manual-upload file paths are the one gap (A.7). `spec.md` §15 lists 21 guardrails, each with the test that proves it. The CI workflow runs ruff, strict mypy, an import-layer contract, migrations, pytest and keyless golden evals, and a nightly keyed job fails on any pass-to-fail flip, attack-success-rate increase or p95 breach. Neither has run in CI: the repo has no git remote. All 27 recorded eval runs are local, git-ignored files (`.gitignore:4`) in which every case that needs a model was skipped because no API key was set, so they cost nothing. AI-tier quality is therefore unmeasured.

### A.7 Where the design stops (verified limits)

- **No connection lifecycle.** There is no OAuth, stored credential, token refresh, connection health or per-connection schedule; `pull()` is the whole contract (`base.py:49-54`).
- **The live client is not hardened.** It has no retry, backoff or rate-limit handling; any non-404 error aborts the pull mid-stream (`client.py:55-60`), and a GraphQL failure silently returns no verified emails (`client.py:80-81`).
- **Revocations are invisible in live mode.** A grant becomes `revoked` only from a webhook-style removal event (`github_mapper.py:303,321`). The live client emits snapshots only, so a removed collaborator keeps its last `active` observation. The end-to-end remediation test passes only because a test-only helper injects the removal event.
- **Unchanged snapshots re-land on every pull.** Member, branch-protection, `SECURITY.md` and file-listing snapshot ids embed the pull time (`client.py:129`, `:179`, `:189`, `:222`), so each live pull adds new raw files and observation rows even when nothing changed.
- **Citation checks confirm presence, not support.** Only dates, providers and timeline text must appear in their quote; the fields that decide pass or fail accept any quote found in the chunk, and a 0.85 word-overlap fallback ignores order and negation (`citations.py:42-47`, `:112`). Run on the repo's own fixtures, a training record marked "In progress" verified as completed and passed; spec A-17 records part of this as a known gap. Tier 3 fixes retrieval quality at 1.0, so a system the model leaves out never lowers confidence (`agent/graphs/tier3.py:189`).
- **Approvals can fail open.** `ccp approvals approve` does not validate `--decision`, so `reject` or a typo approves the draft (`approvals/cli.py:88-90`, `graphs/tier3.py:231-248`). No resume path checks the approved payload hash against the checkpoint, and `ccp remediate rollback` re-grants access without the five gates (`remediation/runner.py:243-289`).
- **Prompt-injection handling only detects.** Tool results in all four agent loops reach the model unfenced, and only the Copilot scans them (`llm/client.py:126-140`, `graphs/copilot.py:350-357`). Detection is 15 fixed English phrases, and a tier-2 hit only caps confidence (`prompt_guard.py:28-45`). Code still decides every status, and every action needs approval.
- **Secrets are redacted only in prompts.** Chunk text goes unredacted to the embedding and rerank APIs, the six secret patterns miss formats such as AWS secret keys, and GH-5 passes a repository whose files were not all read (`retrieval/index.py:139-151`, `secrets_patterns.py:11-20`, `gh5.py:51-54`).
- **Upload paths are not contained.** A manifest entry such as `../globex/report.pdf` is read and stamped with the wrong tenant (`manual/uploads.py:88`). Only the operator writes manifests today, so no tenant can exploit it yet, but it must be closed before customers can upload (D5).
- **A verdict can be lost between two transactions.** It is committed, then announced in a second transaction; a crash in between means it never reaches compliance state or the Investigator, and nothing reconciles them (`evaluators/runner.py:93-106`).
- **One bad record stalls an ordered topic.** An exception inside `OrderedConsumer.handle()` rolls back the whole batch and the cursor never advances, so the same record fails on every run and that tenant's topic stops (`consumers.py:61-72`). Only parallel topics dead-letter. The Investigator is an ordered consumer too, so an exhausted budget or a model error stops it the same way.
- **The model budget parks deterministic tests.** One daily budget per tenant is checked before the tier is known, so after $5 of spend even tier-1 tests park, and no shipped command un-parks them (`evaluators/runner.py:151-153`, `:231-236`).
- **The change-driven path skips identity resolution and indexing.** Only full runs resolve identities and refresh the index (`compliance_state/run.py:65-67`), so a GitHub account first seen after the last full run stays unlinked, and GH-1 and HR-1 can pass for a terminated employee until the next one.
- **Replay breaks once a cited document changes.** Replay looks chunks up in the live index, which drops superseded chunks, so earlier tier-2 and tier-3 verdicts can no longer be replayed, although the stored request still holds the fenced text (`replay/rebuild.py:168-173`). Verdicts also store no rule version.
- **Safe only as one process.** With more than one consumer, ordered cursors can skip rows that commit out of order, and a stale verdict can replace a fresh one (`consumers.py:62-71`, `writer.py:67-77`). The shipped single-process flow avoids both.
- **The impact table is code.** Test ids are hard-coded in `requests_for_entity` (`impact.py:149-209`), although `spec.md` Layer 7 says the mapping is a table. A test left out of it is silently never triggered by changes.
- **Teaching scale by design.** Worker processes that each poll one consumer, a local-disk raw zone, no API or UI, and typed reviewer names instead of authenticated identities.

## B. Competitor technical research

The six incumbents keep a current-state store, fed mostly by scheduled syncs (Sprinto also accepts webhooks), and run deterministic tests over it. Audit history differs: run logs or snapshots (Vanta, Drata, Scrut), evidence bound to each audit (Thoropass), or no integration-test history at all (Secureframe). LLMs work around the pass/fail decision, not inside it. None publicly documents an immutable event ledger, bitemporal state or citations verified in code; the closest is Sprinto's automatic grounding check, whose mechanism is not documented. The AI-native entrants differ mainly in where their agents sit and how much they may write. In 2026 the [Delve allegations](https://techcrunch.com/2026/03/22/delve-accused-of-misleading-customers-with-fake-compliance/) made evidence provenance the category's credibility test.

### B.1 Vanta

By its own count the largest catalogue (400+ integrations), and in our reading the most developed agent platform, on a pooled current-state store.

- **Verified:** a pushed integration replaces a resource type in full on every sync, and resources left out are deleted ([Build Integrations overview](https://developer.vanta.com/reference/build-integrations/overview.md)). The push API accepts 11 built-in resource types, plus a flat custom type that only private integrations may use; native integrations have resource kinds of their own ([Resources](https://developer.vanta.com/docs/concepts/resources.md)).
- **Verified:** for synced resources, tests read Vanta's stored copy, and API-introspection tests also record the requests made during the run. The developer docs say pushed data syncs typically hourly and that tests re-run on the next sync, "usually within 24 hours"; [marketing](https://www.vanta.com/compare/drata) says hourly ([Tests](https://developer.vanta.com/docs/concepts/tests.md), [Remediate with MCP](https://developer.vanta.com/docs/quickstart/remediate-with-mcp.md)).
- **Verified:** audit history is pass/fail timelines plus test-snapshot rows holding raw JSON and, for API-introspection tests, the requests made during the run ([test snapshot API](https://developer.vanta.com/api-reference/audits/get-test-snapshot-detail-for-an-evidence-row.md)).
- **Verified:** [custom tests](https://help.vanta.com/en/articles/11345522-creating-custom-tests) are no-code, join at most two sources on one field, cannot be edited after saving, and have no API or MCP path.
- **Verified:** the Agent and the [hosted MCP server](https://developer.vanta.com/docs/vanta-mcp.md) act with the user's permissions; the developer docs say MCP has no read-only mode, though the [MCP FAQ](https://help.vanta.com/en/articles/15461420-vanta-mcp-troubleshooting-and-faq) says write actions need re-authorization with write permissions. Approval steps exist per feature: [custom agents](https://help.vanta.com/en/articles/16397022-create-schedule-and-manage-custom-agents) run autonomously with their creator's permissions and stop at "Needs approval" only for suggested changes, such as policy or SLA updates. Since May 2026 the offboarding workflow deprovisions Zoom and Figma users, and the MCP remediation flow asks before running CLI changes against live resources ([what's new](https://www.vanta.com/whats-new), [Remediate with MCP](https://developer.vanta.com/docs/quickstart/remediate-with-mcp.md)).
- **Verified:** AI quality rests on verifiers. An [LLM evidence evaluator](https://www.vanta.com/resources/build-verifiers-for-messy-problems) passes or flags evidence; Vanta measures it on an expert-labelled dataset, with LLM-judge metrics, and by agreement with auditors' accept-or-flag decisions. No citation-checking mechanism is documented.
- **Verified:** MongoDB Atlas is the primary database ([blog](https://www.vanta.com/resources/how-we-navigated-database-limits-with-a-growing-product)). Vanta's [RCA for Inc-868](https://www.vanta.com/resources/rca-inc-868) (incident 22–27 May 2025) says a code change removed a "domain ID filter", so data pushed through third-party integrations landed in other customers' tenants ([trust updates](https://trust.vanta.com/updates)).
- **Verified:** AI entries on the [subprocessor list](https://trust.vanta.com/subprocessors) include E2B sandboxes, Hatchet workflows, kernel.sh, Reducto and Lakera, with models from OpenAI, Anthropic, Google and Microsoft. [Merge](https://help.vanta.com/en/articles/11345736-how-does-vanta-use-merge) collects data for some HRIS, task-tracker and access integrations.
- **Inferred:** native connectors are scheduled pulls whose internals are unpublished. A [job posting](https://jobs.ashbyhq.com/vanta/0ccbb65f-f675-410a-ae54-1d34575f228a) sets the integrations platform's goal as "declarative, low-code, and no-code patterns, supercharged by AI agents".

### B.2 Drata

Daily deterministic tests, a JSON rule language for custom tests, and agents concentrated in vendor risk and trust.

- **Verified:** enabled tests "run daily with Autopilot", and each run is stored as a test event with raw JSON ([Monitoring](https://help.drata.com/en/articles/13391811-monitoring-overview-new-experience), [Test details](https://help.drata.com/en/articles/13392374-view-and-manage-test-details-new-experience)).
- **Verified:** completing a [custom-connection](https://developers.drata.com/developer-portal/v2/recipes/custom-connections/) upload session "atomically replaces the active dataset" and permanently deletes the previous records.
- **Verified:** custom tests are JSON rules (`all`/`any`, `fact`/`operator`/`value`/`path`) over one resource type per condition group, capped at 70 lines per block ([Advanced editor](https://help.drata.com/en/articles/13403932-advanced-editor-in-the-test-builder-new-experience)). **Inferred:** the schema matches the open-source json-rules-engine.
- **Verified:** no documented feature lets a model decide pass or fail (our reading of the docs). [AI summaries](https://help.drata.com/en/articles/10008053-enable-ai-summaries-for-tests) of failures are labelled "assistive, not authoritative".
- **Verified:** the [MCP server](https://developers.drata.com/developer-portal/v2/mcp-server)'s September 2026 tool table lists 36 tools, 14 of them writes; its [OAuth server metadata](https://mcp.drata.com/.well-known/oauth-authorization-server) also advertises scopes with no documented tool, such as re-running tests and excluding findings. Access is the intersection of granted scopes and the user's role. The [TPRM Agent](https://help.drata.com/en/articles/16880143-getting-started-with-the-tprm-agent) shows the source excerpt behind each criterion and asks before each write; per-checkpoint autonomy settings can let it proceed without pausing, including when recording risk decisions, though the default still asks first.
- **Verified:** HRIS data arrives through Merge's Common Model ([Workday guide](https://help.drata.com/en/articles/14092393-workday-implementation-best-practices)). The full [subprocessor list](https://trust.drata.com/) (51 entries) names OpenAI for SafeBase AI features such as questionnaire answering, Anthropic for AI Agent Governance, and AI vendors including Vellum, Reducto and Browserbase, plus Braintrust, which Drata says it uses only for internal, offline evaluation.
- **Verified:** a [job posting](https://builtin.com/job/senior-platform-engineer-interoperability/9508400) (removed 23 Sep 2026) listed Temporal, Node.js, TypeORM and MySQL as required skills, with NestJS preferred. A [2025 post](https://drata.com/blog/securing-data-at-scale) describes a single-tenant database architecture in which each customer gets its own database partition.
- **Verified:** by default auditors see only [sampled evidence inside the audit window](https://help.drata.com/en/articles/13606011-how-audit-date-ranges-and-evidence-sampling-affect-auditor-access-new-experience); a customer can also [grant an auditor](https://help.drata.com/en/articles/13605649-create-and-add-auditors-to-an-audit) read-only access to the whole application.

### B.3 Secureframe

Breadth through aggregators, latest-sync-only test state, and a write-capable MCP server.

- **Verified:** "Integration tests only evaluate data from the most recent sync", and Secureframe "does not keep historical integration test data in the app" ([Managing connections](https://support.secureframe.com/en/articles/15111617-managing-your-integration-connections)). Syncs run daily, and the page shows connection and sync status with the raw error.
- **Verified:** integration subprocessors include Finch, Leen, WorkOS and OneSchema ([subprocessors](https://secureframe.com/subprocessors)). [Custom integrations](https://secureframe.com/blog/announcing-custom-integrations) accept API or CSV data with customer-defined schemas.
- **Verified:** [Custom Automated Tests](https://support.secureframe.com/en/articles/15111245-custom-automated-tests-cat) are no-code conditions that run only once mapped to a control. Changes to built-in tests ship as [versioned updates](https://support.secureframe.com/en/articles/15111262-test-activity-dashboard) that are added automatically after a countdown (14 days by default) or by a Secureframe-set deadline at least three weeks out.
- **Verified:** [Comply AI remediation](https://support.secureframe.com/en/articles/15111264-comply-ai-cloud-remediation-test-guidance) produces copy-paste IaC and CLI fixes, and [AI evidence validation](https://support.secureframe.com/en/articles/15111239-ai-evidence-validation-for-upload-test) is advisory only.
- **Verified:** the hosted [MCP server](https://support.secureframe.com/en/articles/15111553-secureframe-mcp-server-ai-driven-compliance-insights) exposes 100+ tools with create, update and delete, has no read-only mode; Secureframe advises reviewing each action and connecting as a restricted role. Secureframe also holds [FedRAMP 20x Moderate](https://secureframe.com/blog/announcing-fedramp-20x-moderate-authorization).

### B.4 Thoropass

A platform built around its own audit firm, with AI at evidence intake and on the auditor's side.

### B.8 Standards direction

- **Verified:** FedRAMP 20x's [2026 certification rules](https://www.fedramp.gov/2026/providers/20x/rules/fedramp-certification/) require machine-readable JSON valid against FedRAMP's own JSON schemas. They also set a minimum number of automated validation methods per Key Security Indicator: at least 2 for Class C and at least 4 for Class D. [FedRAMP](https://www.fedramp.gov/20x/) stops accepting new Rev5 certifications on 11 Jun 2027.
- **Verified:** [Lula 2](https://raw.githubusercontent.com/defenseunicorns/lula/main/README.md) dropped OSCAL as its working format because it "proved too complex for most teams", while [OSCAL 1.2](https://github.com/usnistgov/OSCAL/releases) added a control-mapping model.
- **Inferred:** keep a simple internal model in which each result records its validation method, observed and recorded times, and hashed evidence links. Export OSCAL, FedRAMP JSON or OCSF at the boundary.

## C. Competitive architecture comparison

## D. Architecture gaps and technical debt

CCP's core design (A.1–A.5) is sound, but the code around it can still record a wrong verdict, lose one, or run an action nobody approved, and CCP cannot yet be measured, fully replayed or run for a customer. Each finding gives today's code, verified at `agentic` `3386899` unless marked otherwise, then what competitors do (with links), the gap, our recommendation, how to build it, the tradeoffs and a priority. P0 means fix before CCP handles any real customer data or relies on a real model's output, P1 means needed for a first production customer, P2 means later, and every effort is our estimate in engineer-weeks.

### D1. Live evidence collection: the connector contract (P0, then P1)

- **Today.**
  - The contract is one method, `pull(tenant, since)` (`ccp/connectors/base.py:49-54`). There is no OAuth, stored credential, token refresh, connection health or schedule. The live GitHub connector takes a single token from the environment (`ccp/config.py:101`, `ccp/connectors/registry.py:33-35`).
  - Ingest never passes `since`, so every run is a full pull (`ccp/ingest/landing.py:100`). Each event commits on its own (`landing.py:45-78`), and connectors run one after another with no error handling (`landing.py:92-102`). A pull that fails halfway keeps what it landed and skips the connectors after it. Nothing in the database marks the run as incomplete; only the step log records the error.
  - Revocations are invisible in live mode. Member and collaborator snapshots always map to `active` grants (`ccp/normalize/github_mapper.py:173-177`, `:207-218`). Only webhook-style removal events produce `revoked` (`github_mapper.py:303`, `:321`), and the live client emits snapshots only (`ccp/connectors/github/client.py:3-6`). A removed collaborator keeps its last `active` observation, so HR-1 and GH-1 cannot return to pass after access is removed, and the remediation loop never closes. The end-to-end test closes it only because a test-only helper injects the removal event (`ccp/connectors/github/fixture.py:157-167`, `:187-205`; `tests/e2e/test_remediation_loop.py:82-86`).
  - Unchanged snapshots re-land on every pull. The fixture reader keys snapshots by the provider's `updated_at` "so an unchanged snapshot dedups to nothing" (`fixture.py:3-5`), but the live client keys member, branch-protection, `SECURITY.md` and file-listing snapshots by the pull time (`client.py:129`, `:179`, `:189`, `:222`). Dedup compares ids, never the stored payload hash (`landing.py:52-65`). The repository snapshot, which carries the collaborator list, is keyed by the repository's `updated_at` (`client.py:135`, `:155`); if GitHub leaves that field alone when collaborators change (unverified), a changed list is dropped as a duplicate.
  - The live client is not hardened. It has no retry, backoff or rate-limit handling, and any error other than 404 aborts the pull (`client.py:55-60`). A failed GraphQL call returns no verified emails (`client.py:80-81`). An exact email match is worth 0.55 of the 0.85 score needed to link two records automatically (`config/identity.yaml:6`, `:15`), so one failed call can leave a GitHub account unlinked, where HR-1 and GH-1 cannot see it.
- **Competitors.** The incumbents document completeness only for their push APIs. Vanta replaces a pushed resource type in full on every sync and deletes what was left out ([Build Integrations overview](https://developer.vanta.com/reference/build-integrations/overview.md)). Drata's custom-connection sessions "atomically replace" the dataset and permanently delete the previous records ([custom connections](https://developers.drata.com/developer-portal/v2/recipes/custom-connections/)). Sprinto's sync sessions are applied or discarded ([Entities Sync API](https://docs.sprinto.com/settings/custom-integrations.md)), and its entity types carry `lastSeenOnSource` ([entity types](https://docs.sprinto.com/ingestion/dashboard-actions/create-and-manage-entity-types.md)). Comp AI's open code reconciles cloud findings only from successful scans ("Only successful scans produce truth") and carries services it did not scan forward as unknown ([reconciliation](https://github.com/trycompai/comp/blob/150fed5ade35be5c37f142b126aa10b1859aa26e/apps/api/src/cloud-security/reconciliation.service.ts#L15-L71)). Secureframe shows each connection's sync status with the raw error, including "Partially Successful" ([Secureframe](https://support.secureframe.com/en/articles/15111617-managing-your-integration-connections)), and Thoropass marks each monitor Healthy, Flagged or Connection Error ([Thoropass](https://help.thoropass.com/en/articles/11367746-how-to-evaluate-a-monitor-and-remediate-exclude-results)). Probo's connector protocol covers OAuth2, API keys, GitHub Apps and workload identity, with reconnect and probe capabilities ([capabilities.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/connectorprotocol/capabilities.go#L28-L68)). Its access-review drivers are tested against 131 recorded API sessions, and a test fails if any recording contains an email outside its synthetic test domains ([cassette test](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/accessreview/drivers/cassette_safety_test.go#L34-L76)).
- **Gap.** CCP cannot tell an account that was removed from one it failed to read. So in live mode it never records a revocation, and if it treated every absence as removal, one failed page would mark live access as revoked. The vendors' replace-and-delete model would erase the history CCP exists to keep. Without a lifecycle and a test harness, every new connector brings these failures back.
- **Recommendation.** Make completeness part of the contract. Each pull records a sync run per data type that ends complete, partial or failed. Only a complete run may turn an absence into a revocation, stored as a new observation, never a delete. Add the connection lifecycle and a conformance harness before adding connectors.
- **How.**
  1. Contract: `pull()` returns events plus one sync-run record per data type (status, counts, pages, error class, cursor), landed in the raw zone and the event log like any other event.
  2. Land a snapshot only when its content changes, keyed by a hash of the payload without the pull time, and record "still present at time T" once per complete run instead. HR-1 and GH-1 judge freshness by a grant's latest observation (`ccp/evaluators/deterministic/hr1.py:4-9`, `ccp/evaluators/deterministic/gh1.py:50-51`), so they must read presence from the run record.
  3. Revoke only from complete runs: the mapper emits a `revoked` observation for each grant missing from a complete run of its data type. Partial and failed runs add and update but never revoke, and tests that depend on removals return `needs_review` while their data type's last run is incomplete.
  4. Harden the client: retry 429 and 5xx with backoff and jitter, honor `Retry-After` and GitHub's rate-limit headers, fail one data type rather than the whole pull, raise on GraphQL errors instead of returning nothing, and isolate connectors from each other. Test each failure with recorded responses.
  5. P1, lifecycle: a connections table per tenant; credentials held by a broker, never in settings; a GitHub App installation instead of a personal token; token refresh; health derived from sync runs (healthy, degraded, auth failed, stale); a schedule per connection; and intake for the membership webhooks the fixture already models (`fixture.py:30-35`), with complete snapshots as the backstop.
  6. P1, harness: record and scrub provider responses (normal, empty, page boundary, 401/403, 429, 5xx mid-listing, timeout), replay them against every connector, and assert that a failed listing never ends a run as complete. Require it for every new connector. A model may draft a connector offline, but the harness and a reviewer decide whether it ships.
- **Tradeoffs.** Stricter runs mean more `needs_review` verdicts while a connector is partial, and customers will see them. A GitHub App adds an install step for each customer. Recorded responses drift as provider APIs change, so they need refreshing.
- **Priority.** P0 for steps 1–4 (about 3–4 engineer-weeks, estimate): a live pull today can keep failing a fixed control or hide an account. P1 for steps 5–6 (about 6–8 engineer-weeks, estimate).

### D2. Citation checks confirm presence, not support (P0)

- **Today.**
  - A quote passes if it appears in the cited chunk, or if 85% of its words appear anywhere in the chunk, in any order and ignoring negation (`ccp/evaluators/citations.py:36-47`).
  - Only some fields must also appear in their quote: dates and providers for HR-3, timeline text for GH-4 (`ccp/evaluators/extraction/__init__.py:30-32`, `:38-40`; `citations.py:112`). Any true-or-false value passes that check (`citations.py:50-52`). So the fields that decide pass or fail, such as `completion_status`, `subject_name_in_document`, `policy_exists` and `timeline_stated`, accept any quote found in the chunk.
  - The repo's own fixture shows the risk. A training record reads "Status: In progress (3 of 5 modules completed)" (`fixtures/acme/hris/documents/training-E1044.md:12`). The probe recorded in A.7 found that a model answer of `completed`, citing that line, verifies, and the HR-3 rule then passes (`ccp/evaluators/rules/hr3.py:51-69`).
  - Tier 3 sets its retrieval factor to 1.0 unless its fallback search loop ran (`ccp/agent/graphs/tier3.py:189`), and it counts a list as covered if it names anything (`ccp/agent/core.py:451-453`). If the model leaves a critical system out of the inventory, HR-4 has nothing to call missing and can pass (`ccp/evaluators/rules/hr4.py:23-28`, `:46-56`) at confidence 1.0, above the 0.70 review gate (`tier3.py:210-217`; `config/evaluation.yaml:5`). Its verifier also accepts quotes from any chunk retrieved during the run, not only the chunks shown to that call (`core.py:428-429`).
  - The Copilot checks only its citation list. It drops failed citations but keeps the answer text as written (`ccp/agent/graphs/copilot.py:372-387`, `:429-436`).
  - `spec.md` A-17 defers stronger checks until support precision is measured (`spec.md:2237`). Nothing has measured it against a real model (D7).
- **Competitors.** No vendor documents citations checked in code. The closest is Sprinto: its August 2026 questionnaire pipeline separates fact extraction from answer writing and adds a grounding check with per-answer sources, but does not document how the check works ([Sprinto](https://docs.sprinto.com/product-updates/august-2026.md)). Vanta checks evidence with an LLM verifier that it measures on expert labels and against auditors' accept-or-flag decisions ([Vanta](https://www.vanta.com/resources/build-verifiers-for-messy-problems)). Drata's vendor-risk agent shows the source excerpt behind each criterion ([TPRM Agent](https://help.drata.com/en/articles/16880143-getting-started-with-the-tprm-agent)). Zania claims citations and confidence scores but publishes no verification step ([Zania](https://www.zania.ai/)), and Probo's vendor-vetting tools store document URLs with no field linking a fact to its source ([Probo](https://github.com/getprobo/probo)). After the 2026 [allegations against Delve](https://techcrunch.com/2026/03/22/delve-accused-of-misleading-customers-with-fake-compliance/), which Delve denies, evidence provenance is the category's credibility test.
- **Gap.** Citations checked in code could be CCP's clearest lead, because no competitor documents them. Today the check marks false passes as verified. That is worse than no check, because an auditor reads "verified" as proof.
- **Recommendation.** A field counts only when its quote supports its value. Anything the checker cannot confirm becomes `needs_review`, never a pass.
- **How.**
  1. Require an exact or contiguous match after whitespace is normalized. Remove the 85% word-overlap fallback and any splicing across sentences.
  2. Add a typed check for every field that decides the result: statuses from a fixed vocabulary in which "in progress" can never support "completed", dates parsed and compared exactly, names matched to the subject, and true-or-false fields backed by an explicit phrase. Negation words send the field to review.
  3. Check each quote only against the chunks shown in that call, and only against the evidence type the field requires.
  4. Tier 3: stop fixing the retrieval factor at 1.0, and add a recall check for lists. Parse the critical-systems table in code, or run a second extraction, and send any disagreement to review.
  5. Copilot: label sentences that no verified citation supports, or drop them.
  6. Test on 200–300 labelled field-and-quote pairs that include splices, swapped dates and negations, and let CI allow zero false accepts on them. Add HR-3 and HR-4 attack cases; all 16 today target GH-4 (D7).
- **Tradeoffs.** Automatic pass rates will fall and review queues will grow. Strict matching rejects some honest quotes broken by PDF line breaks or scanning noise, so normalization needs care. Each evidence type needs its own vocabulary, and labelling needs a named domain expert's time.
- **Priority.** P0: no AI-tier verdict should count until this ships. About 3–4 engineer-weeks plus 1–2 weeks of expert labelling (estimates); the labelled set also serves D7.

### D3. Approvals can fail open (P0, then P1)

- **Today.**
  - `ccp approvals approve` takes `--decision` as free text, defaulting to `approve`, and never checks it (`ccp/approvals/cli.py:88-90`). The tier-3 gate treats any action other than `override` or `regather` as approval (`ccp/agent/graphs/tier3.py:231`, `:244-248`), so `reject` or a typo approves the draft verdict. `ccp agent resume` does check the value (`ccp/agent/cli.py:126-127`).
  - The approval is then recorded as `approved`, whatever the resumed graph did (`ccp/approvals/actions.py:51-54`). `ccp agent resume` writes a human-decided verdict with no approval event at all (`ccp/agent/cli.py:143-145`).
  - Resume checks only the tenant and that the thread is waiting (`ccp/agent/tier3.py:234-240`). The interrupt's approval item stores a payload hash (`ccp/approvals/store.py:79-88`), but nothing compares it with the checkpoint being resumed; only remediation checks a hash (`ccp/remediation/gates.py:77-83`).
  - `ccp remediate rollback` re-adds a removed collaborator with no gate check, no `--live` flag and no typed confirmation (`ccp/remediation/cli.py:111-117`; `ccp/remediation/runner.py:243-289`). It uses the permission saved before removal, or `write` when none was saved (`runner.py:269`).
  - A reviewer is any non-empty typed name (`ccp/approvals/store.py:101-102`).
  - What works: one append-only approvals table with a payload hash, dry run by default, and five gates on the one live action (`gates.py:53-84`).
- **Competitors.** Drata's vendor-risk agent asks before each write by default ([TPRM Agent](https://help.drata.com/en/articles/16880143-getting-started-with-the-tprm-agent)). Vanta's Auto Mode pre-approves eligible agent actions, but "destructive actions continue to require individual approval" ([product updates](https://help.vanta.com/en/articles/11345422-product-updates)), and its MCP remediation flow asks before running CLI changes against live resources ([Remediate with MCP](https://developer.vanta.com/docs/quickstart/remediate-with-mcp.md)). Scrut requires an `Idempotency-Key` on every API write, so a retry cannot apply twice ([Open API](https://developer.scrut.io/)). Probo's open code rejects approval decisions that do not cover exactly the pending tool calls, locks the run while it records them, and lets only owners and admins approve ([approval.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agent/approval.go#L33-L125), [service.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agentexecution/service.go#L100-L157), [policies.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agentexecution/policies.go#L28-L62)), yet no production agent turns approvals on ([agent.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agent/agent.go#L359-L365)). Comp AI's approval is the string `acknowledged`, after which another model call rewrites the fix steps ([remediation](https://github.com/trycompai/comp/blob/150fed5ade35be5c37f142b126aa10b1859aa26e/apps/api/src/cloud-security/remediation.service.ts#L512-L681)), and its rollbacks skip its command denylist ([executor](https://github.com/trycompai/comp/blob/150fed5ade35be5c37f142b126aa10b1859aa26e/apps/api/src/cloud-security/aws-command-executor.ts#L772-L865)), much as CCP's rollback skips its gates.
- **Gap.** In our reading CCP has the strongest approval contract on paper. In code it fails open in three places, and a typed name is not an identity, so an auditor cannot tell who approved what. A rollback writes to a customer's system like any other action.
- **Recommendation.** Treat approvals as data the server checks: a closed set of decisions, a payload hash checked when the approval is used, every write behind the same gates (rollback included), and a signed-in reviewer.
- **How.**
  1. Check the decision value in one shared function on every path. An unknown value fails, and `reject` resumes as `needs_review`, as `actions.reject` already does (`actions.py:68-78`).
  2. On resume, recompute the interrupt payload's hash from the checkpoint and refuse if it differs from the hash the approval item already stores. Lock the thread row so two resumes cannot both run, and write the approval event in the same transaction as the verdict, on every path.
  3. Route rollback through the gate check, with its own approval and typed confirmation. Refuse it when no pre-removal permission was saved, instead of granting `write`.
  4. Test each hole: a typo in the decision, a changed payload, two resumes at once, and a rollback without approval.
  5. P1, with D8's sign-in: reviewers are signed-in users with a reviewer role. For actions that change a customer's system, the reviewer must differ from the requester. The apply step is keyed by proposal id and payload hash, so a retry cannot apply twice.
- **Tradeoffs.** Operators get more steps, and an urgent rollback becomes slower. If speed matters, give rollback a separate emergency role that is logged and reviewed afterwards, rather than skipping the gates. Step 5 waits for user identity (D8).
- **Priority.** P0 for steps 1–4 (about 1.5–2 engineer-weeks, estimate): today a typo approves. P1 for step 5 (about 1–2 engineer-weeks once D8's sign-in exists, estimate).

### D4. Background work is safe only as one process (P0, then P1)

- **Today.**
  - A verdict can be lost between two transactions. `commit_verdict` inserts the verdict, then announces it on the `verdicts` topic in a second transaction (`ccp/evaluators/runner.py:93-106`). If the process dies in between, a retry finds the evaluation key taken and skips the announcement (`runner.py:95-96`; `ccp/evaluators/verdict.py:102-107`), so the verdict never reaches compliance state or the Investigator. No code compares verdicts with state.
  - One bad record stalls an ordered topic. An exception in `handle()` rolls back the whole batch and leaves the cursor in place, so the same record fails on every run (`ccp/ingest/consumers.py:61-72`). Only parallel topics dead-letter (`consumers.py:108-136`). The worker loop catches nothing, so the error also ends the process before later tenants run (`ccp/ingest/worker.py:86-103`). No code reads the dead-letter table or re-drives a record.
  - The Investigator is an ordered consumer on `verdicts` (`ccp/investigation/runner.py:208-212`). It raises the park signal when the model key is missing or the budget is spent (`ccp/investigation/runner.py:82`, `:237-238`), but only parallel consumers handle parking (`consumers.py:101-107`), so the Investigator stops at that record instead, like any other ordered-topic failure. It also calls the model while its batch transaction is open (`ccp/investigation/runner.py:239`, with `consumers.py:62-68`), against the rule in `ccp/ingest/topics.py:3-4`.
  - Several processes would skip rows. Offsets are numbered when a row is inserted but become visible when it commits (`ccp/storage/migrations/0001_schema.sql:37`). An ordered consumer reads past its cursor and jumps to the highest offset it saw (`ccp/ingest/event_log.py:58-66`; `consumers.py:69-71`), so a row that commits late with a lower offset is skipped for good. The worker runs one consumer per process (`ccp/cli.py:552-563`), so the change-driven path needs several processes, and the three normalize consumers all write to the `entities` topic (`ccp/normalize/consumer.py:78-85`, `:91-94`).
  - Several processes could also let a stale verdict replace a fresh one. Claims ignore the partition key, so two evaluations of one subject can run at once (`event_log.py:85-101`). The state writer makes whichever verdict arrives last the head of the chain, even an older one, which it labels `late_event` (`ccp/compliance_state/writer.py:44-51`, `:67-78`). The single-process `ccp run` avoids both problems (`ccp/compliance_state/run.py:49-78`).
  - One model budget parks deterministic tests. The daily budget is checked before the tier is known (`ccp/evaluators/runner.py:151-153`, `:165-166`). Each tenant's cap is $5 (`config/tenants.yaml:10`, `:18`), and tier 2, tier 3, the Investigator and the Copilot all charge the same ledger (`ccp/evaluators/tier2.py:287`, `ccp/agent/tier3.py:264`, `ccp/investigation/runner.py:117`, `ccp/copilot/runner.py:257`). Once it is spent, tier-1 tests park too. Only tests call `requeue_parked` (`ccp/evaluators/runner.py:231-236`), although the budget module says parked records resume when the day rolls over (`ccp/evaluators/budget_gate.py:1-3`).
- **Competitors.** The incumbents do not document their queues. A Drata job posting, removed in Sep 2026, listed Temporal ([posting](https://builtin.com/job/senior-platform-engineer-interoperability/9508400)). Vanta lists Hatchet workflows among its subprocessors ([subprocessors](https://trust.vanta.com/subprocessors)), and a Vanta AI-platform posting asks for durable execution with "checkpointing, retries, human-in-the-loop steps" ([posting](https://jobs.ashbyhq.com/vanta/6d2a60a8-7daf-4482-ab9a-6b87516548d0)). Probo's open code runs agents on Postgres much as CCP does, but each claimed run carries an owner token and a heartbeat lease that recovers stale runs, and a checkpoint is saved after every tool turn ([handler.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agentexecution/handler.go#L42-L120), [run.go](https://github.com/getprobo/probo/blob/7bbe06ab6180d7099f4c4dd20e662520f792f348/pkg/agent/run.go#L796-L800)). Drata's engineering blog argues that "Durability has to cover the decision, not just the execution" ([Drata](https://drata.com/blog/building-harness-engineering)); that is strategy, not shipped architecture.
- **Gap.** The queue design is sound: claims, attempts, dead-letter, parking and budgets. The defects lose or stall work without telling anyone. A lost verdict leaves compliance state wrong, and a stalled topic looks the same as a quiet day.
- **Recommendation.** Fix the single-process defects now. Make the queue safe for several processes before the first customer needs a second worker. Choose a durable workflow engine only after that, and only if the hardened queue still falls short.
- **How.**
  1. Write the verdict and its announcement in one transaction. Add a reconciler that announces any verdict with no state row and reports how many it found.
  2. Give ordered topics a poison-record path: after a set number of failures, move the record to dead-letter with its error, advance the cursor and raise an alert. Catch errors per tenant in the worker loop, and ship commands to inspect and re-drive dead letters.
  3. Move the Investigator to the parallel `investigations` topic, which is declared but unused (`topics.py:25`), so its model calls run outside a transaction and parking works.
  4. Check the budget only before model calls, never for tier 1. Re-queue parked records when the day rolls over, and ship a command to do it by hand.
  5. P1, before a second process: number offsets per tenant and topic from a counter row locked in the producing transaction, as `tenant_sequences` already does for state (`ccp/storage/bitemporal.py:83-92`). Allow one evaluation in flight per subject, and file a late verdict into history without displacing a newer head.
  6. Test two producers whose commits interleave, a poison record, and a crash between a verdict and its announcement.
- **Tradeoffs.** A counter row makes producers on one topic take turns, which caps throughput; at CCP's scale that does not matter yet. One transaction per step means the verdict and its announcement must share a connection. A durable engine such as Temporal or Hatchet would add servers and upgrades to run.
- **Priority.** P0 for steps 1–4 and 6 (about 2–3 engineer-weeks, estimate): even one process can lose a verdict or stall. P1 for step 5 (about 2–3 engineer-weeks, estimate).

- **Competitors.** Cross-tenant mistakes are the failures that have hurt vendors. - **Recommendation.** Contain first and detect second. Fence every untrusted input, tool results included. Send injection hits in the AI tiers to review. Keep secrets out of every outbound call. Resolve every file path inside its tenant's folder.
- **How.**

  3. Make GH-5 return `needs_review`, naming the files, when any file was not read.

  5. P1: switch off action-proposing tools for the rest of a run once it has read untrusted text; record each chunk's source, uploader, hash and trust level; and widen detection beyond 15 English phrases, as a signal only.
- **Tradeoffs.** Injection hits will send some honest documents to review, such as a security policy that quotes an attack phrase as an example. Redaction can lower retrieval quality for chunks that lose words. The rule in step 5 that switches off action tools will end some agent runs early.
- **Priority.** P0 for steps 1–4 (about 2–3 engineer-weeks, estimate): real customer files could cross tenants or reach a vendor unredacted. P1 for step 5 (about 2–3 engineer-weeks, estimate).

- **Today.**

- **Gap.** CCP's history design is ahead of these vendors, but a record that cannot be replayed, or that cannot say which rule decided, proves less than Vanta's snapshot rows. The change-driven path is CCP's freshness advantage, yet it misses the cross-system case it was built for: a terminated employee who still has GitHub access.
- **Recommendation.** Run identity resolution and indexing on the change-driven path now. Then make every verdict reproducible from stored inputs: versioned chunks, a rule version and parameters on every verdict, and the impact table as data.
- **How.**
  1. Resolve identities and refresh the index for each changed entity before the impact step maps it, and re-trigger HR-1 and GH-1 when a new link forms; a `person_links` change already maps to both (`impact.py:157-158`).
  2. P1: keep superseded chunks. Key chunks by document version and content hash, mark old versions superseded instead of deleting them, have replay read by version and hash, and check each raw file's hash when it is read.
  3. P1: add a rule version and the parameters in force to every verdict and to its evaluation key, so a rule change re-decides unchanged evidence and shows in history as a rule change. Before a rule change ships, preview the verdicts it would flip and give customers notice, as Secureframe's countdown does for its test updates.
  4. P1: move the impact table into YAML beside `tests.yaml`, generate `requests_for_entity` from it, and fail CI when any test has no trigger.
  5. P1: make tier-1 replay re-run the rule over the stored observations and compare.
- **Tradeoffs.** Versioned chunks grow storage and embedding cost. A rule version in the key means each rule change re-evaluates every affected subject, which costs model calls on the AI tiers. Resolving identity on every change adds work to the busiest path.
- **Priority.** P0 for step 1 (about 1–2 engineer-weeks, estimate): without it, a change-driven run can keep a terminated employee's pass. P1 for steps 2–5 (about 4–5 engineer-weeks, estimate).

## E. Where agents add value

Agents fit where the input is unstructured text and a person makes the final call: questionnaires, connector drafting, framework mapping, uploaded evidence and remediation. They do not fit pass or fail, compliance status, sync health or identity matching. There, code is cheaper, gives the same answer every time and cannot be prompt-injected. Every agent below proposes, code verifies, and a person or a deterministic runner acts. CCP already runs four agents this way (A.4), so these five opportunities extend a working design. None should ship before the Section D fixes it needs. Code paths are relative to `ccp/` at `3386899`; `tests/`, `config/` and `.github/` sit at the repo root.

**Shared rails, from CCP's own design (A.3, A.4):**

- **Tools only read, and code binds the tenant.** Each tool takes its tenant from a closure and rejects extra arguments (`agent/tools.py:1-8`, `:35-36`). A call to a tool not on the graph's list gets an error (`agent/core.py:339-341`). Next comes one typed registry that marks every tool read, propose or act, with agent tools on a read-only database role. Today they share the application role, which can insert (`storage/db.py:34-36`; `storage/migrations/0005_state.sql:66`).
- **Models extract, code decides.** The model fills a typed schema in which each field cites a chunk and a quote. Code checks the quotes (`evaluators/citations.py:87-129`), and a pure rule makes the decision (`evaluators/rules/__init__.py:1-3`). Confidence is computed, never reported by the model, and missing evidence gives `needs_review` (`evaluators/confidence.py:1-15`). The citation check must test support, not just presence (D2).
- **Untrusted text stays data.** Evidence reaches a prompt only inside a per-call fence (`security/prompt_guard.py:105`). Tool results need the same treatment (D5).
- **Agents propose, a person approves the exact payload, and code acts.** The approval stores a sha256 of the payload (`approvals/store.py:22-24`), and the live gate refuses an edited proposal (`remediation/gates.py:77-83`). First the approval path must fail closed and use signed-in reviewers (D3, D8).
- **Every run is budgeted, recorded and replayable, and evals gate changes.** Runs have token, dollar, time and tool-call caps (`llm/budget.py:22-27`), every step is logged (`observability/steps.py:1-8`), and model-backed records can be replayed (`replay/rebuild.py:1-10`). But replay breaks once a cited document changes (D6). Golden, judge and adversarial suites exist (`config.py:58-62`), but none has run on a real model (D7). A workflow earns lighter review only on measured accuracy, consistency and reviewer agreement, and only for reversible actions ([companion document](https://claude.ai/artifact/LcLvkWo3uFjgQvxgFYAXeF), Section 4.4).
- **MCP starts read-only.** MCP is the protocol AI assistants use to call outside tools, and CCP has no MCP server yet. It should be generated from the same registry (M3), take the tenant from the signed-in session, and accept writes only as approval requests. D8 rates it P2. Vanta, Drata and Secureframe instead let agents act with the user's permissions (B.1–B.3).

**Keep these deterministic:** connecting accounts and collecting evidence, sync completeness and connection health, pass or fail and compliance status, identity matching, exception expiry, applying approved changes, and audit packages. Identity matching already uses logged scoring and a review queue, with no model (`identity/scoring.py:1-13`). Each item is a rule over structured data that an auditor must be able to re-run. The companion target-architecture document places all 14 workflows the same way (its Section 4.3).

### E1. Questionnaire answers with verified citations

- **Why an agent.** Security questionnaires arrive as spreadsheets and portals, in endless phrasings, and every answer must be written and backed by evidence. CCP has no questionnaire feature yet. Its closest parts are tier-2 extraction and the Copilot, whose answer citations are checked for presence only (`agent/graphs/copilot.py:364-383`). Build it as a fixed pipeline, not an open tool loop: retrieve, extract cited facts, set the answer by rule where a question maps to a control, then write. Sprinto runs similar passes with a grounding check, and reports 0.995 faithfulness on a 30-question internal benchmark ([Sprinto, Aug 2026](https://docs.sprinto.com/product-updates/august-2026.md)).
- **Tools and data.** A library of approved answers, append-only and versioned, each tagged with the controls it relies on. Policies and other evidence come through the existing retrieval index under row-level security (`storage/migrations/0008_chunks.sql:55-56`), and current compliance state serves as a read-only cross-check. The questionnaire itself is untrusted input and is fenced like evidence (D5).
- **Validation.** Code checks every citation with the hardened checker (D2): a contiguous quote from a chunk shown to that call, with every deciding value inside it. Code blocks any answer whose tagged control is `fail` or `needs_review` in current state. An answer that cannot be verified becomes "needs input", never a guess. A signed-in person approves before anything is sent (D3, D8). Do not auto-approve "high confidence" answers, an option Drata's SafeBase offers ([AIQA guide](https://help.safebase.io/en/articles/16203206-ai-questionnaire-assistance-aiqa-complete-guide)), until accuracy is measured (D7).
- **Metrics.** Share accepted without edits; citation survival rate; answers that contradict compliance state (target 0); reviewer minutes per questionnaire; cost per answer.

### E2. Connector and check drafting behind a conformance harness

- **Why an agent.** Breadth is CCP's widest gap: three connectors, one of them live, against the 400+ integrations Vanta claims (B.1). A connector is pattern-following code written from unstructured API docs, and a check is a small rule over typed entities. An agent can draft both offline. Tests and an engineer decide what ships, and verdicts at run time stay deterministic. Drata used an offline pipeline to write 1,000+ deterministic tests, each validated against its own test API with up to 3 attempts and reviewed by auditors ([Drata, Dec 2025](https://drata.com/blog/AI-compliance-tests)).
- **Tools and data.** Provider API docs and the upgraded connector contract, with a connection lifecycle, cursors and a completeness record (D1). CCP's pure mappers and rule modules serve as examples, with recorded provider responses and sandbox accounts that CCP owns.
- **Validation.** A conformance harness, a test suite every connector must pass, replays recorded responses: empty listings, the last page, 401 and 403, 429, a 5xx in mid-listing and a timeout. It asserts that a failed listing never reads as empty, that a partial pull is marked incomplete, and that a non-compliant fixture fails. A live run against a sandbox account must succeed, and the requested scopes must cover every read and nothing more. An engineer reviews the code.
- **Metrics.** Engineer-hours per connector; harness pass rate of the first draft; defects in the first 30 days; share of drafted checks accepted.

### E3. Framework mapping proposals

- **Why an agent.** CCP maps 9 controls to a 6-criterion SOC 2 slice and an 8-control ISO 27001 slice, by hand, in YAML (`knowledge/controls.yaml:4-50`, `knowledge/frameworks/soc2.yaml:6-51`, `knowledge/frameworks/iso27001.yaml:6-68`). A catalogue for real customers needs far more, and every new framework means matching requirement text to controls. That is semantic search plus judgement. A requirement takes the worst state of its tests (`knowledge/rollup.py:1-9`), so a wrong mapping changes every status built on it, and a person must accept each change. Drata's Framework Mapping Agent works this way: it proposes with a confidence indicator, leaves weak matches unmatched rather than force a guess, and approves nothing on its own ([Drata](https://help.drata.com/en/articles/16630433-framework-mapping-agent-ai-assisted-control-mapping-for-custom-frameworks)).
- **Tools and data.** Requirement and control text, existing mappings as labelled examples, embeddings over the controls, and a named compliance reviewer with budgeted hours. Start as an offline batch for the frameworks customers ask for.
- **Validation.** Before launch, hold out one mapped framework at a time and predict its mappings. Each proposal cites the requirement and control text, and nothing applies until a signed-in reviewer accepts it (D8). Each accepted change creates a new catalogue version, so an as-of query shows which mapping a status used (D6).
- **Metrics.** Precision and recall at 3 on held-out frameworks; reviewer acceptance rate; days to add a framework.

### E4. Evidence review of uploads

- **Why an agent.** Much manual evidence is documents: policies, training records, access reviews, penetration-test reports and vendors' SOC 2 reports. Reading them needs a model; judging them should not. CCP already works this way for three tests. Tier 2 reads a disclosure policy (GH-4) and a training record (HR-3), and tier 3 reads an access review against a critical-systems list (HR-4). Because these verdicts already rest on model output, their fixes are P0 (D2, D7). The opportunity is to extend the pattern to more evidence types, and to scans and screenshots. Today an upload must be Markdown, text or a PDF with a text layer. A PDF without one is flagged `no_text_layer`, and other files are skipped (`connectors/manual/uploads.py:108-132`, `connectors/manual/pdf_text.py:8-13`).
- **Tools and data.** For each evidence type, a typed extraction schema, a pure decision rule and a freshness window, as tier 2 has today (`evaluators/extraction/__init__.py:25-41`; `knowledge/tests.yaml:50`, `:96`). Uploads are hashed, dated and kept in object storage (M5). Count the evidence types customers upload most before choosing which to build.
- **Validation.** Follow Vanta's verifier rubric: admissibility (dated, attributable, and showing the control was carried out) and adequacy (the right document for the control). Vanta measures its verifier on labelled cases and by agreement with auditors' decisions ([Vanta, Aug 2026](https://www.vanta.com/resources/build-verifiers-for-messy-problems)). A named compliance reviewer first labels a fixed sample, for example 50 per type. Run in shadow mode against those labels, recording each verdict without acting on it. Launch only below an agreed false-accept rate, for example 1%. For vendor reports, the risk owner makes the decision.
- **Metrics.** False-accept rate (target near 0); agreement with reviewers and auditors; stale evidence caught; reviewer minutes saved.

### E5. Remediation by pull request

- **Why an agent.** When a test fails, the cause is not known in advance, so an agent must look through grants, history and code to find it. CCP's Investigator already does this, read-only, for every `fail` or `needs_review` verdict, and proposes actions from a closed list (`investigation/runner.py:1-5`, `knowledge/actions.py:4-11`). One action can run live, removing a GitHub collaborator, behind five gates (`remediation/gates.py:1-9`). The next step is a fix a person can read: a pull request in the customer's infrastructure code, opened by CCP's GitHub App with exactly the approved change. Drata also delivers fixes as pull requests against the customer's Terraform, and Vanta's MCP flow has the customer's own coding agent open a draft pull request ([Drata](https://help.drata.com/en/articles/9930785-drata-compliance-as-code), [Vanta](https://developer.vanta.com/docs/quickstart/remediate-with-mcp.md)). The companion document walks through this flow for a public AWS bucket (its Section 6.2).
- **Tools and data.** The failing verdict and its evidence, the subject's history, canonical entities, and the customer's infrastructure repository, read through the tool registry (M3).
- **Validation.** The proposal cites the findings it fixes, and code checks those citations. A signed-in reviewer approves the exact diff, and the executor opens the pull request only if the payload hash still matches (D3). On this path CCP holds no write access to the customer's cloud. Success is judged by the next complete pull and a deterministic re-run, not by the agent. Today the loop closes only through a test-only fixture overlay (`tests/e2e/test_remediation_loop.py:1-4`), because a live pull cannot see a removal (D1).
- **Metrics.** Median time from fail to pass; share of pull requests merged unchanged; reopen rate within 30 days.

## F. Prioritized engineering roadmap

Fix correctness before breadth. The plan assumes three engineers spending about two-thirds of their time on it, roughly 2 engineer-weeks per calendar week; the rest goes to support and other work. All efforts below are our estimates in engineer-weeks. At that rate the quick wins (about 17–24 engineer-weeks) take about nine to twelve weeks. They fix the defects Section D verified and make AI quality measurable. CCP needs both before it handles real customer data or relies on a real model's output (P0), and they add no new scope. Q11 is the exception: D6 rates it P1, but it is small and M9 builds on it. The medium term (about 38–52 engineer-weeks, months 3–8) builds what a first production customer needs (P1). The long term (months 8–18) builds the differentiators (P2). Its items total about 29–40 engineer-weeks; the rest of that time goes to connectors drafted through L7, catalogue content, a read-only MCP server (D8) and customer requests. The companion target-architecture document designs the medium and long term in more detail.

## G. Executive summary

CCP does not need more connectors or agents next quarter; it needs proof that the verdicts it already makes are right. The findings follow Section D's order, and the five investments below fix and measure first, then build what a first production customer needs.

**Findings**

1. **Live evidence cannot show a removal (D1).** The connector contract is one `pull()` method, with no connection lifecycle, cursor or record of whether a pull was complete (`ccp/connectors/base.py:49-54`). The live GitHub client emits snapshots only, and only removal events revoke a grant (`ccp/connectors/github/client.py:3-6`; `ccp/normalize/github_mapper.py:303`, `:321`). So a collaborator removed upstream stays `active`, and the remediation loop closes only in a test that injects the removal (`tests/e2e/test_remediation_loop.py:82-86`). Any error other than a 404 also aborts the pull mid-stream (`client.py:55-60`).
2. **The citation check can mark a false pass as verified (D2).** A quote passes if 85% of its words appear anywhere in the cited chunk, in any order (`ccp/evaluators/citations.py:36-47`), and the fields that decide pass or fail accept any quote that is present (`ccp/evaluators/extraction/__init__.py:30-40`). A probe on CCP's own fixture showed that a model answer of "completed", citing a training record that reads "In progress", verifies, and the HR-3 rule then passes (`fixtures/acme/hris/documents/training-E1044.md:12`; `ccp/evaluators/rules/hr3.py:51-69`). Tier 3 fixes retrieval quality at 1.0 (`ccp/agent/graphs/tier3.py:189`). No competitor documents citation checks in code, so this could be CCP's clearest lead; today it is worse than no check, because an auditor reads "verified" as proof.
3. **Approvals can fail open (D3).** `ccp approvals approve` accepts any `--decision` value, and the tier-3 gate treats anything but `override` or `regather` as approval, so `reject` or a typo approves the draft verdict (`ccp/approvals/cli.py:88-90`; `ccp/agent/graphs/tier3.py:231`, `:244-248`). Resume never compares the approved payload's hash with the checkpoint (`ccp/agent/tier3.py:234-240`), rollback re-grants access without the five gates (`ccp/remediation/runner.py:243-289`), and a reviewer is any typed name (`ccp/approvals/store.py:101-102`).
4. **Background work is safe only as one process (D4).** A verdict is committed, then announced in a second transaction, so a crash in between loses it (`ccp/evaluators/runner.py:93-106`). One bad record stalls a tenant's ordered topic (`ccp/ingest/consumers.py:61-72`). The Investigator reads such a topic, so a missing model key or a spent budget stops it the same way (`ccp/investigation/runner.py:82`, `:208-212`, `:237-238`). With several workers, rows can be skipped and a stale verdict can replace a fresh one (`ccp/ingest/event_log.py:58-66`; `ccp/compliance_state/writer.py:44-51`, `:67-78`). One $5 daily model budget per tenant is checked before the tier is known, so it also parks deterministic tests (`ccp/evaluators/runner.py:151-153`; `config/tenants.yaml:10`).
5. **Untrusted content and secrets are only partly contained (D5).** Injection handling looks for 15 fixed English phrases, and in tier 2 a hit only caps confidence (`ccp/security/prompt_guard.py:28-44`; `ccp/evaluators/confidence.py:76-78`). Tool results reach the model unfenced (`ccp/llm/client.py:126-140`). Chunk text goes unredacted to the embedding and rerank APIs (`ccp/retrieval/index.py:139`, `:151`; `ccp/retrieval/hybrid.py:231`). An upload manifest entry such as `../globex/report.pdf` is read from another tenant's folder and stamped with the wrong tenant (`ccp/connectors/manual/uploads.py:88`).
6. **Records cannot always be replayed or kept current (D6).** Replay looks chunks up in the live index, so it breaks once a cited document changes (`ccp/replay/rebuild.py:168-173`). Verdicts store no rule version (`ccp/evaluators/verdict.py:72-90`), and the impact table is code (`ccp/evaluators/impact.py:149-209`). Only full runs resolve identities and refresh the index (`ccp/compliance_state/run.py:65-67`), so on the change-driven path a GitHub account first seen after the last full run stays unlinked, and GH-1 and HR-1 can keep passing for a terminated employee until the next full run.
7. **AI quality is unmeasured (D7).** The repo has no git remote, so CI has never run, and all 27 recorded eval runs (`evals/runs/`, 12–15 Sep 2026) were keyless: no case used a token. The nightly gate blocks on any single pass-to-fail flip (`ccp/evals/regress.py:36-41`), which in our reading noise alone will trip on most nights. The judge runs on the tier-2 model, Haiku 4.5 (`ccp/config.py:73`, `:75`), whose earliest retirement date, 15 Oct 2026, has passed ([Anthropic](https://platform.claude.com/docs/en/about-claude/model-deprecations)). Published eval numbers are rare in the category; Vanta and Sprinto publish some ([Vanta, Jun 2026](https://www.vanta.com/resources/vanta-ai-quality-evaluation-maturity-model), [Sprinto](https://docs.sprinto.com/product-updates/august-2026.md)), so a measured false-pass rate would set CCP apart.
8. **There is no product surface or operating model (D8).** CCP is teaching-scale by its own spec (`spec.md:1`). It is a command line with two fixture tenants in YAML, worker processes that each poll one consumer, and a raw zone on local disk (`pyproject.toml:12`; `config/tenants.yaml:1-3`; `ccp/ingest/worker.py:67-103`; `ccp/config.py:49`, `:133-135`). It has no API, UI, sign-in, roles, onboarding, deployment or purge path, and `spec.md` line 3 still says no code exists.
9. **Competitors lead on breadth and surface; CCP can lead on proof (B, C).** Vanta claims 400+ integrations, against CCP's three connectors, one of them live (B.1, A). Yet none of the six incumbents documents an immutable event ledger, bitemporal state or citation checks in code, no AI-native entrant publishes a citation-verification step, and no incumbent documents what a partial sync from a native connector does. Most incumbents let agents act with the user's permissions over MCP, while CCP's agents only read and propose (A.4). After the 2026 [allegations against Delve](https://techcrunch.com/2026/03/22/delve-accused-of-misleading-customers-with-fake-compliance/), which Delve denies, results a buyer can check are an open position, in our reading.

**Invest in these first**

| # | Investment | Effort | Why first |
| --- | --- | --- | --- |
| 1 | Fail closed: a private remote with CI, approvals, upload paths, verdict writes, dead letters for ordered topics, and a model budget that never parks tier 1 (Q1–Q4, Q6, Q7) | 4.5–6 engineer-weeks | Small fixes; today a typo approves, a crash can lose a verdict, and one bad record stops a tenant's topic |
| 2 | Citations that test support, measured on real models (Q5, Q13) | 5–7 engineer-weeks, plus a reviewer's labelling time | No AI-tier verdict should count until "verified" means supported and the false-pass rate is known |
| 3 | Contain untrusted content and secrets, and keep records current and replayable (Q8–Q11) | 4.5–6.5 engineer-weeks | Needed before real customer files arrive; every verdict stays explainable after a document or rule changes |
| 4 | Live evidence a customer can trust: hardened GitHub pulls, then the connection lifecycle, completeness record and conformance harness (Q12, M1) | 9–12 engineer-weeks | Live mode cannot see a removal today, and more connectors in today's shape would multiply that failure |
| 5 | Durable execution, a typed tool registry, and an API with signed-in users and roles (M2, M3, M4) | 14–20 engineer-weeks | Work survives crashes and deploys, and every approval has an accountable reviewer |

Together that is about 37–52 engineer-weeks, all estimates: roughly 19 to 26 weeks, or four to six months, for three engineers who spend about two-thirds of their time on this plan (about 2 engineer-weeks per calendar week). It includes every quick win, which together address each P0 gap in Section D, the work Gate 1 checks. The rest of the medium term (M5–M9, about 18–24 engineer-weeks) covers the remaining Gate 2 items, so a first production customer is about six to nine months away at this capacity. The differentiators follow: questionnaire answers with verified citations (E1, L1), evidence review of more upload types (E4, L2) and remediation by pull request (E5, L3).

**Decisions needed**

- Leadership: confirm the capacity the plan assumes, three engineers at about two-thirds time, and name an owner for each workstream. Hold new connectors until the completeness record and the conformance harness exist (D1, F).
- Compliance: name a domain expert to label evidence for GH-4, HR-3 and HR-4, starting with about 1–2 weeks of labelling, and agree the false-pass limit that Gate 1 requires (D2, D7, Q13).
- Security and legal: before real customer data arrives, settle retention terms with each model provider and opt out of Voyage model training (Q9). Agree retention and erasure terms for customer data before any retention lock is set (M5, D8).
- AI: pin dated model ids now (Q13). Choose the judge's model family, which adds a vendor and its data terms, and choose tier 2's next model by a paired comparison before a retirement notice for Haiku 4.5 forces the move (D7, M8).
- Engineering: choose where the private remote lives and turn on CI this week (Q1). Agree the crash and deploy tests that decide whether the hardened Postgres queue is enough or CCP moves to DBOS Transact (M2).
- Product: choose the first customer's systems for M7: AWS through a read role, an identity provider, and HRIS data through an aggregator, which adds a vendor that handles customer HR data. Confirm that fixes go by pull request first, with no write role in customer clouds for now (E5, F).
