One Proof, Two Rulebooks

How a framework, a control, and a piece of evidence fit together in this project.

First, a kitchen.

This project has five kinds of things.

A rulebookThe project calls it a framework. There are two: SOC 2 and ISO 27001.
One rule in itCalled a requirement. Like "remove access when people leave."
A promise you keepCalled a control. The one real thing you do that satisfies rules from both rulebooks.
A checkCalled a test. The exact way the computer looks to see if the promise is kept.
ProofCalled evidence. A roster, a training certificate, a GitHub setting. The tag on the extinguisher.

Here they are, hooked together.

A real one from the project: the promise that people lose access when they leave.

Then the answer goes back up. Once.

Why bother with the middle?

Rulebooks ask. A promise answers. A check looks. Proof is what it looks at.

the real names, in case you meet them in the code

promisecontrol · controls.yaml, ids like CTL-ACCESS-REVOKE. Nine of them.
checktest · tests.yaml, ids like HR-1, GH-1. Ten of them. Each says which proof types it reads.
proofEvidence row · has an evidence_type such as hr_roster, training_record, repo_settings
stampverdict in compliance_state · carries control_ids, so one row rolls up under every rulebook
