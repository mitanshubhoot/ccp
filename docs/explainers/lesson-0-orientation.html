ccp, Lesson 0, told simply

A Robot Hall Monitor for Company Rules

The repo builds a program that watches a company's systems, checks them against rulebooks, remembers what it believed and when, and asks a human before it ever touches anything. Ten pictures, one story, same order as the professor's lesson.

Two honest notes first.

There are three verdict tiers, not four. Tier 1 decides with plain rules, tier 2 reads one document, tier 3 reads two and pauses for a human. The "four" that exists is the test harness's four levels: unit, component, workflow, e2e (spec A-15, D4). Two different counts, two different words.

The spec's first line is stale. Line 3 says no code exists yet. The code is the current truth; spec section 22 (A-1 to A-94) records every place the build drifted from the plan. The README still says A-92, but the review commit added A-93 and A-94.

Bonus

Three things a senior reviewer asks

Why is Postgres the queue, the vector store, and the state store?

D7 (spec.md 2360 to 2374): one container, and row-level security then covers the queue, the chunks, and the state with one policy. Cost: no horizontal scaling, and the checkpoint schema is a soft spot (A-40).

Why does no model return a status?

A model that says pass or fail can be tricked into a verdict. A model that returns cited fields can only be tricked into a field, and citation checking drops it.

What does the keyless suite prove?

The mechanisms, using the same fenced prompts a model would see. Model behaviour is the nightly keyed job's business.
