01 · Architecture

Code decides, models propose, people approve

Evidence flows left to right through code that sets every status. Agents read through one gateway and can only propose; code renders each fix, the customer applies it, and only the next sync confirms it.

CODE DECIDES

Every status comes from a rule

  • A versioned rule over pinned facts sets PASS, FAIL or PARTIAL. Tier-2 models only extract typed fields, with pointer citations that code checks.
  • Absence counts only from a complete sync; a partial or denied read gives needs_review.
  • Verdict, state row and announcement commit in one transaction.

MODELS PROPOSE

Agents read, then propose

  • Agents run as bounded queue jobs (turns, tokens, cost, time), at most one run per evidence state.
  • Every tool is typed, bound to the tenant in code and checked by a fail-closed policy.check. Code, not the model, chooses every live read.
  • A run ends with a draft or a fix chosen by id from the catalogue, never a write.

PEOPLE DECIDE

Suggest, never apply

  • Code renders the Terraform change, commands and console steps from a versioned template and checks them offline before anyone sees them.
  • A signed-in member approves drafts by payload hash, never the requester; accepting a fix is a record only.
  • No pull request, executor or write credential: a fix is confirmed only when a later read sees it.

02 · Deployment

Where CCP runs on AWS

One cell per region from the same Terraform: one image as api and worker behind PgBouncer, RDS PostgreSQL with a read replica as the record, a write-once raw zone, and checkpoints in an account CCP cannot write to.

INVENTORY

Small on purpose

  • Per cell: RDS PostgreSQL 17 (Multi-AZ) and a read replica, PgBouncer in transaction mode, S3 in two accounts, KMS keys, one image run as api and worker, a load balancer, Cognito, CloudWatch.
  • Outside services: Anthropic (US cell), Bedrock (EU cell), Voyage, Langfuse Cloud, GitHub (read only).

NOT ADDED

Deliberately left out

  • Kafka, Redis, Temporal, Kubernetes, a vector database, self-hosted observability, an MCP gateway, a code sandbox.
  • Any write role, executor or GitHub App in a customer's account: CCP suggests fixes and applies none.

SCALE

Cells, a pooler, a replica

  • The readiness report reads the replica only while its lag is under 30 seconds; one large tenant can get a partition of its own.
  • A tenant lives in one cell and a process serves only its cell. eu-1 calls models through Bedrock in its region; a dedicated cell is the same module.

03 · Sequence

A public S3 bucket, from first read to a confirmed fix

The AWS worked example, suggest-only: a rule finds the bucket open, code looks up who changed it and where it lives in Terraform, renders a checked fix, the customer applies it, and the next read confirms it.

DETECT

Code finds the FAIL

  • Every page lands write-once with a hash and a completeness record before it is mapped.
  • The failing rule names the bucket, so the rule itself explains the failure: no model is needed and nothing parks.

LOOK UP

Code picks every read

  • Config history in 7-day windows, the CloudTrail events that can change the setting, and a search of the organization's Terraform; 10 resources and 30 days at most.
  • Each response lands raw before its typed row. A model never chooses a live read or its parameters.

SUGGEST AND CONFIRM

Applied by the customer

  • Code fills the fix's template and checks parameters, commands, syntax and scope; a fix that fails a check is never offered.
  • Accepting is a record. Only a verdict on evidence observed after the suggestion confirms it; a FAIL within 30 days reopens it.

04 · Flowchart

How evidence becomes a verdict

Every path ends in a verdict that code wrote. Gaps in the data abstain as needs_review; a model's only job is to fill typed fields that code checks before a rule reads them.

TIER 1

Rules over facts

  • Pure functions over observations, keyed by rule version and pinned inputs.
  • Tier 1 never waits on a model budget.

TIER 2

Extract, then rule

  • Haiku 5.5 fills a typed schema with pointer citations (segment ids, JSON Pointers). Code checks each one, then a rule decides.
  • A refusal or failed check gives needs_review. A second reader runs before any AI-derived PASS.

ROLLUP

Over who should be there

  • The rollup counts the expected population, not only rows that exist, and marks stale or unassessed subjects.
  • No PASS over a partial or stale population.

05 · State machine

The life of a fix suggestion

CCP suggests fixes and applies none. Code renders and checks each one; a person may accept or dismiss it, but only a later read of the customer's systems confirms it, and a FAIL within 30 days reopens it.

RENDERED

Code writes what is shown

  • The model, or code when the rule explains the failure, picks a fix by id and its parameters. It never writes a command or a diff.
  • Code fills the versioned template and checks params, commands, syntax, scope and placeholders. A failure is recorded, never offered.

NO EXECUTION

The customer applies it

  • No pull request, write credential or executor. The suggestion is a Terraform change, commands and console steps to copy.
  • Accept and dismiss are records; a dismissal says why.

DONE MEANS READ

Confirmed by evidence

  • A verdict on evidence observed after the suggestion that no longer names the resource confirms it.
  • ccp fixes metrics reports time to confirm and the 30-day reopen rate.

06 · ER / data model

The evidence chain behind every verdict

One chain from a raw provider page to the read that confirmed a fix: evidence, FAIL, lookups, investigation, suggestion, confirming verdict. Rows are appended and superseded, never edited.

APPEND ONLY

History is kept

  • Verdicts and state rows are insert-only; a correction supersedes with a reason and never rewrites.
  • As-of queries show what was true, and what CCP believed, at any time.

REBUILDABLE

Verdicts carry their inputs

  • rule_version and the manifest of pinned inputs identify each verdict.
  • Model requests and responses are stored, so an AI-derived verdict is rebuilt from stored outputs, never re-sampled.

VERIFIABLE

Without trusting the database

  • A per-tenant hash chain covers raw objects and every row above.
  • Hourly signed checkpoints sit in a compliance-mode bucket in a separate account; ccp audit verify checks them.
  • As-of audit packages carry raw pointers and chain proofs and verify offline with a public key.

07 · Layer stack

Guardrails, by where they are enforced

Twenty controls on the five surfaces a finding crosses. Each one is enforced outside the model: by CCP code with a test, by Postgres or AWS, or by a signed-in person.

FAILS CLOSED

Default deny

  • An unknown tool, tenant, decision or model price is refused, not guessed.
  • Kill switches per workflow, per tool and per tenant, plus one that parks all model work.

MEASURED

Autonomy is earned

  • Five runs per case, pass^k, false PASS and false FAIL reported apart.
  • A draft skips review only in a reversible, low-impact class whose published snapshot meets the bar, within a daily budget and a 10% sample, and is demoted automatically.

PAGED

What wakes someone

  • Chain verification fails, a replay mismatch, the cross-tenant canary fails, or AI work parks for 30 minutes.
