02 · Deployment · CCP target architecture

Where CCP runs on AWS

One cell per region from the same Terraform: one image as api and worker behind PgBouncer, RDS PostgreSQL with a read replica as the record, a write-once raw zone, and checkpoints in an account CCP cannot write to.

INVENTORY

Small on purpose

  • Per cell: RDS PostgreSQL 17 (Multi-AZ) and a read replica, PgBouncer in transaction mode, S3 in two accounts, KMS keys, one image run as api and worker, a load balancer, Cognito, CloudWatch.
  • Outside services: Anthropic (US cell), Bedrock (EU cell), Voyage, Langfuse Cloud, GitHub (read only).

NOT ADDED

Deliberately left out

  • Kafka, Redis, Temporal, Kubernetes, a vector database, self-hosted observability, an MCP gateway, a code sandbox.
  • Any write role, executor or GitHub App in a customer's account: CCP suggests fixes and applies none.

SCALE

Cells, a pooler, a replica

  • The readiness report reads the replica only while its lag is under 30 seconds; one large tenant can get a partition of its own.
  • A tenant lives in one cell and a process serves only its cell. eu-1 calls models through Bedrock in its region; a dedicated cell is the same module.
